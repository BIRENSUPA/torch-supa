# torch-supa Base Operator Understanding

This skill explains how to reason about operators in `torch-supa`: where an operator belongs, how it is registered, how a PyTorch call reaches `PrivateUse1` / SUPA code, and how to debug the path. It is based on:

- `docs/sphinx/source/torch_supa_op_dispatch_debug.rst`
- `docs/sphinx/source/op_repo_registration.rst`

## When to use

Use this skill when the user asks about:

- Which repo should own an operator change.
- How to register an operator in `torch-supa`.
- How `torch-supa` native operators are called.
- How a `torch.xxx` op reaches `RegisterSUPANative.cpp`, `SUPANativeFunctions`, or a kernel.
- How structured ops work in this framework.
- How `DispatchStub` maps a shared ATen implementation to device-specific kernels.
- How to debug an operator path with gdb or source inspection.
- Why a PrivateUse1/SUPA op differs from CUDA behavior.

For a high-level framework overview, use `foundations/torch-base-framework/SKILL.md` first.

## Operator ownership classification

Before suggesting code changes, classify the operator ownership.

### 1. `torch-supa`

Use `torch-supa` ownership when:

- The operator is called through a native `torch.xxx` API.
- The desired behavior is mostly the original PyTorch CUDA behavior.
- Only small source patches are needed to make CUDA-origin code work for `PrivateUse1`.
- The operator belongs to torchvision support currently maintained in `torch-supa`.

Important note:

- `torch-supa` maintains patch/source changes only.
- It normally does not require extra manual operator registration in `torch-supa`.
- Registration is generated by `torch-supa` codegen after parsing `native_functions.yaml`.

### 2. `torch-supa`

Use `torch-supa` ownership when:

- The operator is called through a native `torch.xxx` API.
- It needs a SUPA-specific or operator-library rewrite for performance or behavior.
- It must override the default `torch-supa` native implementation.
- It is a base/infrastructure operator such as copy, empty, pin memory, record stream, or related device/runtime integration.

Main registration file:

- `torch_supa/csrc/aten/supa_native_functions.yaml`

Main implementation locations:

- `torch_supa/csrc/aten/ops/*.cpp`
- `torch_supa/csrc/aten/ops/kernels/`

### 3. `torch_supa_ext`

Use `torch_supa_ext` ownership when:

- The operator is custom.
- The operator belongs to a third-party library integration.
- The operator is not a native PyTorch `torch.xxx` ATen operator.

Follow the rules of the `torch_supa_ext` repo for these operators.

## torch-supa registration model

### Registration list

Main file:

- `torch_supa/csrc/aten/supa_native_functions.yaml`

The operator name must exist in PyTorch `native_functions.yaml` unless it is under the custom schema section.

Important lists:

- `supported`
  - Registers operators to the `PrivateUse1` dispatch key.
  - Used for normal SUPA device-level overrides.

- `autograd`
  - Registers operators to `AutogradPrivateUse1`.
  - Used when `torch-supa` must override backward or implement custom autograd behavior.

- `perf_supported`
  - Intended for operators that already have complete functionality in `torch-supa`, but need a higher-performance SUPA override.
  - The referenced docs describe this as under development.

- `custom`
  - Internal/debug/fused custom schemas.

Example shape:

```yaml
backend: SUPA
cpp_namespace: at::supa
supported:
  - _addmm_activation.out
  - _pin_memory
  - _cdist_forward
perf_supported:
  - xxxx
autograd:
  - renorm
custom:
  - func: _get_data_ptr(Tensor self) -> int
```

### Generated registration files

Generated files live under:

- `torch_supa/csrc/aten/generated/Register*.cpp`

The most important one for PrivateUse1 is:

- `torch_supa/csrc/aten/generated/RegisterSUPANative.cpp`

These files are generated by `script/codegen_native` from the environment's PyTorch `native_functions.yaml` plus `supa_native_functions.yaml` choices.

The generated wrapper normally handles:

- Dispatcher registration through `TORCH_LIBRARY_IMPL`.
- Device checks.
- Device guards.
- Profiling hooks.
- Structured-op output allocation and proxy outputs.
- Calls into `at::supa::SUPANativeFunctions` or structured `impl_supa`.

## torch-supa implementation patterns

### Normal SUPANativeFunctions implementation

For normal operators, add definitions under:

- `torch_supa/csrc/aten/ops/`

Pattern:

```cpp
namespace at::supa {

Tensor SUPANativeFunctions::_cdist_forward(
    const Tensor& x1,
    const Tensor& x2,
    const double p,
    c10::optional<int64_t> compute_mode) {
  // operator-specific implementation
}

} // namespace at::supa
```

### Structured operator implementation

Structured ops are usually marked on the `.out` variant in PyTorch `native_functions.yaml` with `structured: true`.

Use structured handling when:

- The PyTorch schema has `structured: true`.
- The functional variant delegates to an `.out` variant.
- You want to reuse PyTorch's meta function for shape inference and preprocessing.

Implementation pattern:

```cpp
SUPA_IMPL_FUNC(_addmm_activation)(
    const Tensor& self,
    const Tensor& mat1,
    const Tensor& mat2,
    const Scalar& beta,
    const Scalar& alpha,
    bool use_gelu,
    const Tensor& result) {
  addmm_out_impl(
      const_cast<Tensor&>(result),
      self,
      mat1,
      mat2,
      beta,
      alpha,
      use_gelu ? Activation::GELU : Activation::RELU);
}
```

For structured ops, always identify the real registered schema first. Often the correct entry is `op.out`, not the functional `op` name.

### AutogradPrivateUse1 implementation

Use the `autograd` list when the operator needs custom backward.

Typical pattern:

```cpp
class RenormFunction : public torch::autograd::Function<RenormFunction> {
 public:
  static at::Tensor forward(
      torch::autograd::AutogradContext* ctx,
      const Tensor& self,
      const Scalar& p,
      int64_t dim,
      const Scalar& maxnorm);

  static std::vector<at::Tensor> backward(
      torch::autograd::AutogradContext* ctx,
      std::vector<at::Tensor> grad_outputs);
};

Tensor SUPANativeFunctions::renorm(
    const Tensor& self,
    const Scalar& p,
    int64_t dim,
    const Scalar& maxnorm) {
  return RenormFunction::apply(self, p, dim, maxnorm);
}
```

### SUPA kernel implementation

Add lower-level kernels under:

- `torch_supa/csrc/aten/ops/kernels/`

`SUPANativeFunctions` implementations can directly call these SUPA kernel launch wrappers.

The referenced docs state that `torch-supa` currently does not plan to migrate the old 1xx framework's Ptfrontend and kernel selection features.

## torch-supa native operator call stack

`torch-supa` adapts PyTorch ATen CUDA source code to `PrivateUse1` device operators and provides it as an operator library:

- `libtorch_supa.so`

`torch-supa` links against and calls this library.

The high-level call stack for a native op is:

```text
Python torch API
  -> PyBind-bound PyTorch C++ API
  -> PyTorch Dispatcher
  -> DispatchKey selection, e.g. CPU / CUDA / PrivateUse1
  -> torch-supa generated Register*.cpp registration
  -> PrivateUse1 wrapper in RegisterSUPANative.cpp
  -> torch-supa adapted ATen implementation or torch-supa override
  -> DispatchStub or direct device implementation
  -> SUPA/PrivateUse1 kernel
```

Important boundary:

- The dispatcher path before the device-specific code is provided by the official CPU PyTorch package and is not modified here.
- In `torch-supa`, operator call analysis usually starts from `torch_supa/csrc/aten/generated/Register*.cpp`.

## Structured op tracing recipe

For a structured op:

1. Find the operator in PyTorch `native_functions.yaml`.
2. Check whether the `.out` variant has `structured: true`.
3. Check whether the functional variant has `structured_delegate: xxx.out`.
4. In generated `RegisterSUPANative*.cpp`, find the `wrapper_PrivateUse1_*` wrapper.
5. Inspect the generated structured wrapper:
   - It constructs `structured_<op>_out` or a similar generated class.
   - It calls `op.meta(...)` for shape inference and preprocessing.
   - It calls `op.impl(...)` or `op.impl_supa(...)` for actual computation.
   - It copies proxy outputs back when needed.
6. Search PyTorch source for the meta function:
   - `TORCH_META_FUNC(op)`
7. Search implementation functions:
   - `TORCH_IMPL_FUNC(op)`

Two implementation cases:

- Shared CPU/CUDA structured implementation in `aten/src/ATen/native/*Ops.cpp`
  - It often calls a `DispatchStub` for device-specific dispatch.

- Device-specific structured implementation in `aten/src/ATen/native/cuda/*.cu`
  - It may directly call the CUDA-origin kernel template adapted by `torch-supa`.

## DispatchStub tracing recipe

A `DispatchStub` has three pieces:

1. Declaration:

```cpp
DECLARE_DISPATCH(unary_fn, sgn_stub)
```

2. Definition:

```cpp
DEFINE_DISPATCH(sgn_stub);
```

3. Device implementation registration:

```cpp
REGISTER_DISPATCH(sgn_stub, &sgn_kernel_cuda)
```

In upstream PyTorch, `REGISTER_DISPATCH` registers CUDA kernels for CUDA device type. In `torch-supa`, this macro is adapted so CUDA-origin kernels register for `PrivateUse1`.

Tracing method:

1. Find the structured or native implementation.
2. Identify the stub call, such as `sgn_stub(device_type(), *this)`.
3. Search for `DECLARE_DISPATCH` and `DEFINE_DISPATCH` of that stub.
4. Search for `REGISTER_DISPATCH(stub_name, ...)`.
5. The registered function is usually the final device kernel entry.

## Debugging operator issues

### Build for debugging

Use DEBUG builds when breakpoints are needed:

```bash
DEBUG=on python3 setup.py build
```

`DEBUG=on` can propagate into the `torch-supa` subrepo. However, if `third-party/torch-supa/torch_supa/lib/libtorch_supa.so` already exists, this command only rebuilds `torch-supa`.

To force rebuilding `torch-supa` for debugging:

```bash
CLEAN_TORCH_SUPA=on python3 setup.py clean
DEBUG=on python3 setup.py build
```

### Common issue category: CUDA vs PrivateUse1 branch differences

Many upstream PyTorch code paths check device type explicitly. A tensor in this framework has device type `PrivateUse1`, not `CUDA`. This can change branch behavior.

Typical symptom:

- CUDA path has special handling.
- PrivateUse1 does not satisfy the CUDA branch condition.
- Code falls into a CPU-like or unsupported path.
- The fix may be either a `torch-supa` override or a `torch-supa` patch depending on where the branch lives.

Decision rule:

- If the problematic branch is in `libtorch_cpu.so` or shared ATen C++ code that cannot be patched invasively here, prefer re-registering/overriding in `torch-supa`.
- If the problematic branch is in `libtorch_cuda.so`, CUDA-origin `.cu` code, or patched torch-supa source, fix it through a `torch-supa` patch.

Examples mentioned in the docs:

- `renorm`: PrivateUse1 follows CPU-like `toAccumulateType`, promoting float to double, while CUDA does not support the double kernel path.
- `index_put`: for `PrivateUse1` with `accumulate=True`, code may fail to enter the CUDA/XPU branch that calls `index_put_with_sort_stub`.
- Similar reasons apply to operators such as `std`, `var`, `pdist`, and `cdist`.

### Common issue category: torch-supa patch logic

`torch-supa` maintains patch directories, including:

- `torch_supa/patch_privateuse1`
- `torch_supa/patch_torch2x`

Patch omissions or wrong patch logic can cause operator failures. To inspect the effective source, check:

- `third-party/torch-supa/build/_deps/pytorch-src`

### Common issue category: torch-supa infrastructure operators

`torch-supa` implements and registers infrastructure operators such as:

- `_pin_memory`
- `copy_`
- `empty`
- `record_stream`

These can involve complex behavior such as H2D, D2H, D2D, P2P, type casting, and contiguous conversion. Treat them as `torch-supa` maintained logic when debugging.

## Standard answer template

When answering an operator understanding question:

1. Classify ownership: `torch-supa`, `torch-supa`, or `torch_supa_ext`.
2. Identify registration path:
   - `supa_native_functions.yaml` list: `supported`, `autograd`, `perf_supported`, or `custom`.
   - Generated file: usually `RegisterSUPANative.cpp` for `PrivateUse1`.
3. Identify implementation type:
   - Normal `SUPANativeFunctions`.
   - Structured `SUPA_IMPL_FUNC` / `impl_supa`.
   - `AutogradPrivateUse1` custom autograd.
   - `torch-supa` native adapted ATen implementation.
   - Custom `.su` / `.cu` kernel.
4. Provide the call stack from Python to final device implementation.
5. If debugging, state whether the likely issue is:
   - CUDA vs PrivateUse1 branch difference.
   - Missing or wrong `torch-supa` patch.
   - `torch-supa` override/infrastructure implementation issue.
6. Point to exact files and symbols to inspect next.

## Do not do

- Do not assume every `torch.xxx` operator should be implemented in `torch-supa`; classify ownership first.
- Do not register the functional name when PyTorch schema requires the structured `.out` entry.
- Do not edit generated `Register*.cpp` as the source of truth.
- Do not treat `supa` as a C++ dispatch key. The C++ dispatch key is `PrivateUse1`; `supa` is the renamed device/backend name.
